# mcC2S 脅威モデル

mcC2S は「サーバー参加時にクライアントの Mod・リソースパック等を照合し、許可されていない構成を弾く」ための
チート対策 Mod です。このドキュメントは **何を守れて、何を守れないか** を正直に書きます。
過大な期待で運用すると、かえって危険だからです。

## 大前提: クライアントは攻撃者の制御下にある

プレイヤーの PC 上で動くコードは、そのプレイヤー(=攻撃者になり得る人)が自由に改造・観測できます。
サーバーが「クライアントが正直に報告している」ことを **暗号だけで保証することは原理的にできません**
(TPM 等によるハードウェア認証は Java の Mod からは使えません)。

したがって mcC2S の目標は「完全な排除」ではなく、次の 2 つです。

1. **暗号学的に強く保証できる部分**(通信路・プロトコル)を確実に守る。
2. **保証できない部分**(クライアントの誠実さ)は、攻撃コストを引き上げ、検知手段を重ねる。

## 暗号で保証していること(プロトコル層)

| 脅威 | 対策 |
|---|---|
| 偽サーバーが、プレイヤーの構成情報を収集する | クライアントは信頼ファイルの Ed25519 サーバー公開鍵にピン留め。署名不正なチャレンジには一切応答しない |
| 他人(別プレイヤー)の正規な応答の使い回し | ハンドシェイクをログイン名に束縛(署名・鍵導出に含む) |
| 正規応答の盗聴・再送(リプレイ) | 毎回のサーバー nonce・双方の一時鍵(X25519)で鍵が変わる。1 ハンドシェイクは 1 回しか使えず、失敗でも消費 |
| 通信途中の改ざん・報告範囲(scope)の縮小・ダウングレード | チャレンジは全フィールドが署名対象。添付・判定は AEAD(ChaCha20-Poly1305)で全バイトが認証される |
| pack_secret を持たない第三者の偽クライアント | 鍵導出に pack_secret が入るため、ECDH が成立しても AEAD を通れない |
| 後日の鍵漏洩による過去ログの復号 | 一時鍵(前方秘匿性)。ただし判定内容自体は秘密情報ではない |
| 不正な長さ・巨大入力による DoS/メモリ枯渇 | すべてのフィールドに上限。パースは AEAD 認証の後 |
| ログの偽造・端末エスケープ注入(Mod 名に改行等を仕込む) | 制御文字を含む項目はデコード時に拒否。ログ出力は必ずエスケープ |
| mcC2S 本体の改造版(ハッシュが公式一覧に無い) | 作者のリリース鍵で署名された公式ビルド一覧と照合 |

これらは `core` のテストで攻撃シナリオごとに検証しています(`HandshakeTest` など)。

## 暗号では保証できないこと(残余リスク)

正直に書きます。決意のある攻撃者に対して、以下は **破られ得ます**。

### 1. クリーンコピー攻撃
チートを実行しつつ、`mods/` とは別の場所に置いた「正規の jar」を読んでそのハッシュを報告する。
- 対策(緩和): 測定証明(`ProofContext`)。サーバーが同じファイルを持つ項目について、毎回ランダムな鍵で
  ファイル全体の HMAC を要求するため、ハッシュ一覧を丸ごと偽装するだけの偽クライアントは通れない。
  ただし **正規ファイルを実際に持っている** 攻撃者は通れる。

### 2. リレー攻撃
チートクライアントが、同一 PC で動く別の正規クライアントにチャレンジを中継して応答を代行させる。
接続束縛(ログイン名)は「同じアカウントを使う本人」には効かない。
- 対策(緩和): プレイ中のランダム再検証、Mod 側での接続固有情報の追加束縛(M2 で検討)、サーバー側の異常検知。完全な防止は不可能。

### 3. pack_secret の抽出
信頼ファイルは正規プレイヤー全員に配布されるため、プレイヤー自身は抽出できる。
pack_secret の役割は「そのサーバーの信頼ファイルを持たない第三者(汎用バイパスの配布者など)」を弾くことで、
**サーバーの参加者による抽出は防げません**。漏洩が疑われる場合は pack_secret をローテーションします
(旧鍵は猶予期間だけ受理できます)。

### 4. mcC2S 本体の改造・リバースエンジニアリング
プロトコルは公開前提(OSS)で設計してあり、**秘密は鍵にだけ置きます**(Kerckhoffs の原則)。
難読化はコードの解析コストを上げるだけで、保証ではありません。
サーバー側の公式ビルド照合は、改造版の「素朴な使用」を防ぎますが、
公式ビルドのハッシュを名乗り測定証明を正規コピーで通す攻撃(上記 1・2)は防げません。

### 5. 仮想環境・エミュレーション
クライアントの JVM 自体をフックされた場合(`-javaagent` など)、報告内容を書き換えられます。
`AGENT` / `OTHER_CODE` の報告で「素朴な」エージェントは見つかりますが、JVM の外側からの改変は見えません。

## 想定する現実的な効果

- 配布されている汎用チート Mod・不正なリソースパック・シェーダーを導入したクライアントの排除
- 「サーバーの信頼ファイルを持たない」汎用バイパスの排除
- 再検証とログにより、ログイン後の導入・不審な挙動を検知
- 攻撃者に、サーバーごとの個別対応(信頼ファイル入手 + 正規コピーの保持 + 中継)を強いることによるコスト上昇

「これを入れれば不正は 0 になる」ものではありません。ほかの対策(サーバー側の挙動検知など)と併用してください。

## プライバシー

クライアントはサーバーへ **Mod ID・バージョン・ファイルの SHA-256・リソースパック名とハッシュ・
JVM エージェントのハッシュ・Minecraft/ローダー/mcC2S のバージョン** を送ります。
ファイルパス・ユーザー名・OS・全 JVM 引数・IP 等は送りません。
信頼ファイルを持つサーバー(=運営者が配布した相手)にのみ応答します。詳細は `PROTOCOL.md` のマニフェストを参照してください。

## 運用上の注意

- `server_identity` の秘密鍵はサーバーの外に出さない(信頼ファイルには公開鍵のみ入る)。
- 信頼ファイルは Mod パックに同梱して配布してよいが、公開掲示板には載せない。
- 導入時は `mode = "audit"` で誤検知を洗い出してから `enforce` にする。
