# プロキシ経由サーバー(Velocity / BungeeCord 等)への対応余地

**現状の対応範囲は「Forge/NeoForge サーバーへの直結」です。** プロキシ経由は未対応ですが、
将来追加できるように、コアを次の性質で作ってあります。

## 現在の設計が担保していること

1. **`core` は輸送層に依存しない。** ハンドシェイクは「バイト列を受け取りバイト列を返す」だけで、
   Minecraft のパケットや特定のローダーを参照しません。分割送信(`Fragmenter` / `Reassembler`)も
   任意の輸送路で使えます。
2. **接続束縛(`context`)が差し替え可能。** 直結では `Contexts.player(uuid)` ですが、
   `Contexts.compose(...)` で「どのプロキシ/どのバックエンド向けか」などを追加でき、
   サーバーとクライアントが同じ値を使わない限り署名検証に失敗します。
3. **プロトコル版とスイートが署名・鍵導出に含まれる。** 将来の拡張(新スイート、チケット等)は
   ダウングレードなしで導入できます。
4. **判定(ポリシー)と輸送が分離されている。** `PolicyEvaluator` はマニフェストと設定だけを入力にします。

## 想定される将来の方式(未実装・案)

### 案 A: プロキシでハンドシェイクを終端する(推奨案)
- プロキシ側プラグインが `core` を使ってハンドシェイクとポリシー判定を行う。
- バックエンドは既定で何もしない(または「プロキシ署名済みチケット」を検証する)。
- 利点: 検証がネットワークの入口に 1 箇所で済む。クライアント側 Mod は変更不要。
- 課題: プロキシ側の Mod 一覧(baseline)の持ち方、Velocity の modded 対応(FML ハンドシェイクの通し方)。

### 案 B: バックエンドで検証し、プロキシは素通し
- プロキシが FML のログイン/設定フェーズのカスタムペイロードを透過的に中継できる場合のみ可能。
  (Velocity では専用プラグインが必要になる場合が多く、環境依存が大きい。)
- `context` にプロキシ/バックエンド識別子を加えて、別バックエンドへのチャレンジ流用を防ぐ。

### 案 C: プロキシ署名チケット
- プロキシで検証に成功したら、短い有効期限つきの Ed25519 署名チケット
  `{uuid, manifestDigest, 有効期限, 対象バックエンド}` を発行し、バックエンドが署名だけ検証する。
- バックエンドでの重い検証(全 jar のハッシュ検証)を省ける。

## 実装時に確認すること

- プロキシ経由でも、サーバーが見るプレイヤー UUID とクライアントが持つ UUID が一致するか
  (オンラインモード転送・Velocity modern forwarding では一致する)。
- カスタムペイロード(コンフィギュレーションフェーズ)をプロキシがどう扱うか。
- 信頼ファイル/サーバー識別鍵を「プロキシ」と「バックエンド」のどちらに紐づけるか。
